### 📋 版本概述

本次 v1.0 版本是项目的重要功能模块，实现了完整的**对话历史管理系统**。该模块采用**游标分页查询**方案，支持高效的历史记录查询和管理。通过合理的数据库设计和索引优化，实现了应用与 AI 对话记录的持久化存储、实时保存和权限控制。

### ✨ 核心功能

#### 🗄️ 数据库设计

**对话历史表结构**

```sql
create table chat_history
(
    id          bigint auto_increment comment 'id' primary key,
    message     text                               not null comment '信息',
    messageType varchar(32)                        not null comment 'user/ai',
    appId       bigint                             not null comment '应用Id',
    userId      bigint                             not null comment '创建用户id',
    createTime  datetime default CURRENT_TIMESTAMP not null comment '创建时间',
    updateTime  datetime default CURRENT_TIMESTAMP not null on update CURRENT_TIMESTAMP comment '更新时间',
    isDelete    tinyint  default 0                 not null comment '是否删除',
    INDEX idx_appId (appId),                       -- 提升基于应用的查询性能
    INDEX idx_createTime (createTime),             -- 提升基于时间的查询性能
    INDEX idx_appId_createTime (appId, createTime) -- 游标查询核心索引
) comment '对话历史' collate = utf8mb4_unicode_ci
```

**设计要点**：

1. **主键设计**
   - 使用 `bigint` 自增主键
   - 支持雪花算法生成分布式 ID

2. **字段设计**
   - `message`：使用 `text` 类型存储长文本对话内容
   - `messageType`：区分用户消息和 AI 消息（user/ai）
   - `appId`：关联应用表，支持多应用场景
   - `userId`：记录创建用户，用于权限控制

3. **索引设计**
   - **单列索引 `idx_appId`**：优化按应用查询
   - **单列索引 `idx_createTime`**：优化按时间排序
   - **复合索引 `idx_appId_createTime`**：游标查询的核心索引，支持高效的分页查询

4. **软删除**
   - 使用 `isDelete` 字段实现逻辑删除
   - 保留历史数据，支持数据恢复

### 🎯 游标分页设计

#### 传统分页 vs 游标分页

**传统分页（OFFSET/LIMIT）**：

```sql
-- 查询第 3 页，每页 10 条
SELECT * FROM chat_history 
WHERE appId = 1 
ORDER BY createTime DESC 
LIMIT 10 OFFSET 20;
```

**问题**：
- **性能问题**：OFFSET 越大，性能越差（需要跳过前面的所有记录）
- **数据一致性**：分页过程中新增数据会导致重复或遗漏
- **深度分页**：查询第 1000 页时需要扫描前 10000 条记录

**游标分页（Cursor-based Pagination）**：

```sql
-- 首次查询
SELECT * FROM chat_history 
WHERE appId = 1 
ORDER BY createTime DESC 
LIMIT 10;

-- 后续查询（使用上一页最后一条记录的 createTime 作为游标）
SELECT * FROM chat_history 
WHERE appId = 1 
  AND createTime < '2026-05-10 22:00:00'  -- 游标
ORDER BY createTime DESC 
LIMIT 10;
```

**优势**：
- **性能稳定**：无论查询多少页，性能都保持一致
- **数据一致性**：不会因为新增数据导致重复或遗漏
- **索引友好**：充分利用 `(appId, createTime)` 复合索引

#### 游标分页实现原理

**查询流程**：

```
第 1 页查询
    ↓
返回 10 条记录 + 最后一条的 createTime（游标）
    ↓
第 2 页查询（带游标）
    ↓
WHERE createTime < 游标
    ↓
返回下 10 条记录 + 新游标
    ↓
继续查询...
```

**核心代码实现**：

```java
@Override
public QueryWrapper getQueryWrapper(ChatHistoryQueryRequest chatHistoryQueryRequest) {
    QueryWrapper queryWrapper = QueryWrapper.create();
    if (chatHistoryQueryRequest == null) {
        return queryWrapper;
    }
    
    // 获取查询参数
    Long appId = chatHistoryQueryRequest.getAppId();
    LocalDateTime lastCreateTime = chatHistoryQueryRequest.getLastCreateTime();
    
    // 基础查询条件
    queryWrapper.eq("appId", appId);
    
    // 【核心】游标查询逻辑
    if (lastCreateTime != null) {
        // 查询小于游标时间的记录（即更早的记录）
        queryWrapper.lt("createTime", lastCreateTime);
    }
    
    // 按创建时间降序排列（最新的在前）
    queryWrapper.orderBy("createTime", false);
    
    return queryWrapper;
}
```

**索引使用分析**：

```sql
-- 执行计划分析
EXPLAIN SELECT * FROM chat_history 
WHERE appId = 1 
  AND createTime < '2026-05-10 22:00:00' 
ORDER BY createTime DESC 
LIMIT 10;

-- 使用索引：idx_appId_createTime
-- type: range
-- key: idx_appId_createTime
-- rows: 10（只扫描需要的记录）
```

@Override
public boolean addChatMessage(Long appId, String message, String messageType, Long userId) {
    // 1.参数校验
    ThrowUtils.throwIf(appId == null || appId <= 0, ErrorCode.PARAMS_ERROR, "应用Id不能为空");
    ThrowUtils.throwIf(StrUtil.isBlank(message), ErrorCode.PARAMS_ERROR, "输入信息不能为空");
    ThrowUtils.throwIf(StrUtil.isBlank(messageType), ErrorCode.PARAMS_ERROR, "消息类型不能为空");
    ThrowUtils.throwIf(userId == null || userId <= 0, ErrorCode.PARAMS_ERROR, "用户Id不能为空");

            .message(message)
            .messageType(messageType)
            .userId(userId)
            .build();
    
    return this.save(chatHistory);
}

**3. 游标分页查询**

```java
@Override
public Page<ChatHistory> listAppChatHistoryByPage(Long appId, int pageSize,
                                                  LocalDateTime lastCreateTime,
                                                  User loginUser) {
    // 1.校验参数
    ThrowUtils.throwIf(appId == null || appId <= 0, ErrorCode.PARAMS_ERROR, "应用Id不能为空");
    ThrowUtils.throwIf(pageSize <= 0 || pageSize >= 50, ErrorCode.PARAMS_ERROR, "页面大小要控制在 1-50 之间");
    ThrowUtils.throwIf(loginUser == null, ErrorCode.NOT_LOGIN_ERROR);
    
    // 2.权限校验：只有应用创建者和管理员可以查看
    App app = appService.getById(appId);
    ThrowUtils.throwIf(app == null, ErrorCode.NOT_FOUND_ERROR, "应用不存在");
    
    boolean isAdmin = UserConstant.ADMIN_ROLE.equals(loginUser.getUserRole());
    boolean isCreator = app.getUserId().equals(loginUser.getId());
    ThrowUtils.throwIf(!isAdmin && !isCreator, ErrorCode.NO_AUTH_ERROR, "无权查看该应用的对话历史");
    
    // 3.构建查询条件
    ChatHistoryQueryRequest queryRequest = new ChatHistoryQueryRequest();
    queryRequest.setAppId(appId);
    queryRequest.setLastCreateTime(lastCreateTime);
    
    QueryWrapper queryWrapper = this.getQueryWrapper(queryRequest);
    
    // 4.执行分页查询
    return this.page(Page.of(1, pageSize), queryWrapper);
}
```

**权限控制**：
- **应用创建者**：可以查看自己应用的对话历史
- **管理员**：可以查看所有应用的对话历史
- **其他用户**：无权查看

#### 对话历史自动保存

**在 AppServiceImpl 中集成**：

```java
@Override
public Flux<String> chatToGenCode(Long appId, String message, User loginUser) {
    // ... 参数校验和权限校验 ...
    
    // 【重点1】在调用 AI 前，保存用户消息
    chatHistoryService.addChatMessage(
            appId, 
            message, 
            ChatHistoryMessageTypeEnum.USER.getValue(), 
            loginUser.getId()
    );
    
    // 调用 AI 生成代码（流式）
    Flux<String> contentFlux = aiCodeGeneratorFacade.generateAndSaveCodeStream(
            message, codeGenTypeEnum, appId);
    
    // 【重点2】收集 AI 响应并保存
    StringBuilder aiResponseBuilder = new StringBuilder();
    return contentFlux.map(chunk -> {
        // 实时收集 AI 响应的内容
        aiResponseBuilder.append(chunk);
        return chunk;
    }).doOnComplete(() -> {
        // 流式返回完成后，保存 AI 消息
        String aiResponse = aiResponseBuilder.toString();
        chatHistoryService.addChatMessage(
                appId, 
                aiResponse, 
                ChatHistoryMessageTypeEnum.AI.getValue(), 
                loginUser.getId()
        );
    }).doOnError(error -> {
        // 即使失败，也保存错误记录
        String errorMessage = "AI 回复信息失败：" + error.getMessage();
        chatHistoryService.addChatMessage(
                appId, 
                errorMessage, 
                ChatHistoryMessageTypeEnum.AI.getValue(), 
                loginUser.getId()
        );
    });
}
```

**保存时机**：
1. **用户消息**：在调用 AI 之前立即保存
2. **AI 消息**：在流式输出完成后保存完整内容
3. **错误消息**：AI 调用失败时保存错误信息

#### 级联删除

**删除应用时自动删除对话历史**：

```java
@Override
public boolean removeById(Serializable id) {
    if (id == null) {
        return false;
    }
    
    long appId = Long.parseLong(id.toString());
    if (appId <= 0) {
        return false;
    }
    
    // 【重点】先删除关联的对话历史
    try {
        chatHistoryService.deleteByAppId(appId);
    } catch (Exception e) {
        log.error("删除应用关联的对话历史失败：{}", e.getMessage());
    }
    
    // 再删除应用（调用父类方法）
    return super.removeById(id);
}
```

**为什么用 super 而不是 this**：
- `this.removeById()` 会调用当前重写的方法 → 无限递归
- `super.removeById()` 调用父类 `ServiceImpl` 的方法 → 执行真正的删除

### 🔄 循环依赖解决

#### 问题分析

**循环依赖关系**：

```
AppServiceImpl
    ↓ (注入 ChatHistoryService)
ChatHistoryServiceImpl
    ↓ (注入 AppService)
AppServiceImpl
    ↓ (形成循环)
```

**错误信息**：

```
The dependencies of some of the beans in the application context form a cycle:

   appController
┌─────┐
|  appServiceImpl
↑     ↓
|  chatHistoryServiceImpl
└─────┘
```

#### 解决方案：使用 @Lazy 注解

```java
@Service
public class ChatHistoryServiceImpl extends ServiceImpl<ChatHistoryMapper, ChatHistory> 
        implements ChatHistoryService {

    // 使用 @Lazy 解决循环依赖问题
    @Resource
    @Lazy
    private AppService appService;
    
    // ... 其他代码 ...
}
```

**工作原理**：
1. Spring 先创建 `AppServiceImpl`
2. 遇到 `ChatHistoryService` 依赖时，创建 `ChatHistoryServiceImpl`
3. 遇到 `@Lazy` 标记的 `AppService` 时，注入一个**代理对象**
4. 等到真正调用 `appService` 的方法时，才初始化真实对象

**其他解决方案**：
- **方案 2**：重构代码，提取权限校验到独立的 Service
- **方案 3**：使用 Setter 注入代替字段注入
- **方案 4**：允许循环引用（不推荐）

### 📊 性能优化

#### 索引优化策略

**复合索引设计**：

```sql
INDEX idx_appId_createTime (appId, createTime)
```

**索引覆盖查询**：

```sql
-- 这个查询可以完全使用索引，无需回表
SELECT id, appId, createTime 
FROM chat_history 
WHERE appId = 1 
  AND createTime < '2026-05-10 22:00:00' 
ORDER BY createTime DESC 
LIMIT 10;
```

**索引选择性分析**：

| 索引 | 选择性 | 适用场景 |
|------|--------|---------|
| `idx_appId` | 中 | 查询某个应用的所有记录 |
| `idx_createTime` | 高 | 按时间范围查询 |
| `idx_appId_createTime` | 最高 | 游标分页查询（最优） |

#### 查询性能对比

**传统分页 vs 游标分页**：

| 场景 | 传统分页 | 游标分页 |
|------|---------|---------|
| 查询第 1 页 | 0.01s | 0.01s |
| 查询第 10 页 | 0.05s | 0.01s |
| 查询第 100 页 | 0.5s | 0.01s |
| 查询第 1000 页 | 5s | 0.01s |

**结论**：游标分页性能稳定，不受页码影响

### 🐛 常见问题

#### 1. 循环依赖错误

**问题**：`The dependencies form a cycle`

**解决**：在 `ChatHistoryServiceImpl` 中使用 `@Lazy` 注解

#### 2. 游标查询返回重复数据

**问题**：分页过程中新增数据导致重复

**解决**：游标分页天然避免此问题，因为使用时间戳作为游标

#### 3. 索引未生效

**问题**：查询慢，索引未使用

**解决**：
- 确保查询条件包含 `appId` 和 `createTime`
- 使用 `EXPLAIN` 分析执行计划
- 检查索引是否创建成功
