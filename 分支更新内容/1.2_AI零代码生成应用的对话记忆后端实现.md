### 版本概述

本次 `1.2` 分支聚焦于 **AI 零代码生成应用的对话记忆后端实现**。这一部分的目标，不再只是“把一次 AI 生成请求跑通”，而是让系统具备 **连续对话、上下文继承、会话隔离、历史持久化、重启后恢复记忆** 的能力。

在 `0.4 ~ 0.7` 阶段，项目已经完成了 AI 代码生成、流式输出、SSE 前后端联通等核心流程；而 `1.2` 的重点，是把这些一次性能力升级为 **真正可持续交互的 AI 应用能力**。

这一版后端实现，核心上完成了三件事：

1. 为每个应用 `appId` 构建独立的对话记忆空间，避免不同应用的上下文串线。
2. 使用 `Redis + 数据库` 的双层方案，兼顾运行期记忆读写速度与长期历史可追溯性。
3. 在 AI 调用前后自动记录用户消息与 AI 回复，并在重新创建 AI 服务实例时将历史记录重新装载到记忆窗口中。

---

### 核心目标

#### 为什么必须做“对话记忆”

如果系统没有对话记忆，那么 AI 每次收到的都只是当前这一条 prompt。这样会直接带来几个问题：

1. AI 无法记住上一轮已经生成过什么。
2. 用户无法在上一轮结果基础上继续修改，比如“不要生成网站，告诉我你刚才做了什么”。
3. 不同应用如果共用同一个 AI 服务实例，历史上下文会污染，A 应用的问题可能影响 B 应用的回答。

因此，对话记忆模块的本质目标是：

- 让 AI 在同一应用内具备连续对话能力。
- 让不同应用之间的上下文严格隔离。
- 让服务重建后仍然能恢复最近的聊天上下文。

#### 本版采用的总体方案

本项目最终采用的是 **“应用级独立 AI Service + Redis 运行期记忆 + MySQL 历史持久化”** 的组合方案。

也就是说：

- 每个 `appId` 对应一个独立的 `AiCodeGeneratorService`
- 每个服务实例内部绑定一个独立的 `MessageWindowChatMemory`
- `MessageWindowChatMemory` 底层存入 Redis
- 同时，所有用户消息 / AI 消息也会落库到 `chat_history` 表
- 当 AI 服务实例因为缓存过期或系统重启而重新创建时，再从数据库中回填最近的对话历史

### 功能拆解

#### 1. AI 接口层支持 MemoryId

对话记忆能够成立，第一步是让 AI 接口具备“区分不同会话”的能力。

在 [YuCodeMother-Backend/src/main/java/com/yupi/yucodemotherbackend/ai/AiCodeGeneratorService.java](/d:/0%20Postgraduate/JAVA/JAVA%20Project/Java_Project_Practices/Yupi_Projects/yu-ai-code-mother/YuCodeMother-Backend/src/main/java/com/yupi/yucodemotherbackend/ai/AiCodeGeneratorService.java:1) 中，HTML 代码生成方法定义为：

```java
HtmlCodeResult generateHtmlCode(@MemoryId int memoryId, @UserMessage String userMessage);
```

这里的 `@MemoryId` 是整个对话记忆机制的入口。它告诉 LangChain4j：

- 这不是一条孤立请求
- 这条消息属于某个特定记忆空间
- 同一个 `memoryId` 的多次调用，应当共享同一段上下文

这一步解决的是“框架层支持多轮对话”的问题。

#### 2. Redis 聊天记忆存储配置

运行期记忆最终存放在 Redis 中，配置类是 [RedisChatMemoryStoreConfig.java](/d:/0%20Postgraduate/JAVA/JAVA%20Project/Java_Project_Practices/Yupi_Projects/yu-ai-code-mother/YuCodeMother-Backend/src/main/java/com/yupi/yucodemotherbackend/config/RedisChatMemoryStoreConfig.java:1)。

核心 Bean 如下：

```java
@Bean
public RedisChatMemoryStore redisChatMemoryStore() {
    String redisUser = resolveRedisUser();
    return RedisChatMemoryStore.builder()
            .host(host)
            .port(port)
            .user(redisUser)
            .password(password)
            .ttl(ttl)
            .build();
}
```

这部分的作用是：

- 从 `spring.data.redis` 下读取主机、端口、用户名、密码、TTL
- 构造 LangChain4j 使用的 `RedisChatMemoryStore`
- 作为所有 `MessageWindowChatMemory` 的统一底层存储

#### 3. Redis ACL 用户名兼容处理

这一版里有一个非常关键的实现细节：`resolveRedisUser()`。

```java
private String resolveRedisUser() {
    if (StringUtils.hasText(username)) {
        return username;
    }
    if (StringUtils.hasText(user)) {
        return user;
    }
    if (StringUtils.hasText(password)) {
        return "default";
    }
    return null;
}
```

这段逻辑的意义并不只是“补个默认值”，而是在修复一个真实运行时问题：

- 当前项目使用的 `langchain4j-community-redis` 版本中
- 如果只传 `password` 不传 `user`
- 底层可能不会按 ACL 方式构造 Jedis 认证连接
- 最终在访问 Redis 时出现 `NOAUTH Authentication required`

因此这里的处理顺序是：

1. 优先使用标准配置项 `spring.data.redis.username`
2. 兼容旧字段 `user`
3. 如果只配置了密码但没配置用户名，则默认使用 Redis ACL 的 `default`

这一步解决的是“配置上看似写了密码，但运行时其实没有真正认证成功”的问题。

#### 4. 每个 appId 构建独立 AI 服务实例

真正实现“应用级会话隔离”的关键，在 [AiCodeGeneratorServiceFactory.java](/d:/0%20Postgraduate/JAVA/JAVA%20Project/Java_Project_Practices/Yupi_Projects/yu-ai-code-mother/YuCodeMother-Backend/src/main/java/com/yupi/yucodemotherbackend/ai/AiCodeGeneratorServiceFactory.java:1)。

项目没有简单地让所有请求共用一个 AI Service，而是改成了：

- 通过工厂类统一创建 AI Service
- 通过 `appId` 获取或创建对应的服务实例
- 为每个服务实例绑定独立的记忆对象

核心入口：

```java
public AiCodeGeneratorService getAiCodeGeneratorService(long appId) {
    return serviceCache.get(appId, this::createAiCodeGeneratorService);
}
```

这段逻辑表示：

- 如果当前 `appId` 的 AI Service 已经在缓存中，直接复用
- 如果没有，则调用 `createAiCodeGeneratorService(appId)` 创建一个新的

#### 5. Caffeine 本地缓存服务实例

为了避免每次请求都重新构建 AI 服务实例，工厂类中加入了 Caffeine 缓存：

```java
private final Cache<Long, AiCodeGeneratorService> serviceCache = Caffeine.newBuilder()
        .maximumSize(1000)
        .expireAfterWrite(Duration.ofMinutes(30))
        .expireAfterAccess(Duration.ofMinutes(10))
        .build();
```

这个缓存的设计目的很明确：

- 减少频繁创建 AI Service 的开销
- 让同一应用在一段时间内保持上下文连续
- 又避免实例永久不释放导致内存膨胀

这里采用了双过期策略：

- `expireAfterWrite(30min)`：写入后 30 分钟过期
- `expireAfterAccess(10min)`：10 分钟不访问则过期

这意味着：

- 活跃应用会持续复用同一个 AI Service
- 长时间不用的应用会自动释放实例

#### 6. 创建独立聊天记忆窗口

`createAiCodeGeneratorService(appId)` 是这一版最核心的方法之一：

```java
MessageWindowChatMemory chatMemory = MessageWindowChatMemory
        .builder()
        .id(appId)
        .chatMemoryStore(redisChatMemoryStore)
        .maxMessages(20)
        .build();
```

这里有几个关键点：

##### `id(appId)` 的作用

这是“会话隔离”的决定性字段。

如果没有给 `MessageWindowChatMemory` 设置唯一 id，那么多个应用最终会写到同一组 Redis key，造成：

- 不同应用的上下文混用
- AI 回答受到其他应用历史消息干扰
- 对话内容错乱

而把 `appId` 作为 memory id 后：

- 应用 1 的上下文只属于应用 1
- 应用 2 的上下文只属于应用 2
- 每个应用天然拥有自己的对话记忆空间

##### `chatMemoryStore(redisChatMemoryStore)` 的作用

这表示记忆窗口本身不是纯内存对象，而是接入 Redis 做底层存储。好处是：

- 对话消息不会只存在 JVM 临时内存里
- 服务实例重建后仍有机会恢复记忆
- 多轮对话的上下文可以在进程级别之外保留一段时间

##### `maxMessages(20)` 的作用

这里使用的是“消息窗口”模型，而不是无限堆积全部上下文。

这样做的原因是：

- 避免上下文无限膨胀
- 控制 prompt 长度和 token 成本
- 保证近期对话优先进入模型上下文

#### 7. 从数据库回填历史记忆

只用 Redis 还不够，因为：

- Redis 可能过期
- 本地缓存实例可能被淘汰
- 服务重启后 JVM 内对象一定消失

所以在 AI Service 创建后，系统还会从数据库回填最近的聊天历史：

```java
chatHistoryService.loadChatHistoryToMemory(appId, chatMemory, 20);
```

这一步把 `chat_history` 表中的历史消息重新压入 `MessageWindowChatMemory`，从而实现：

- 服务重建后恢复最近上下文
- Redis 丢失后仍可从 MySQL 恢复
- 历史对话不仅“能查”，还“能重新参与推理”

### 数据持久化设计

#### 1. 为什么不能只靠 Redis

如果只把对话消息放进 Redis，会有几个问题：

1. Redis 本质更适合作为高速缓存，不适合作为唯一历史档案。
2. TTL 到期后，对话就彻底消失。
3. 后台无法提供对话历史查询、审计、分页加载等能力。

因此本项目选择把：

- Redis 作为 **运行期短期记忆**
- MySQL 作为 **长期历史存储**

#### 2. 对话历史数据表承载长期存储

聊天历史实体是 [ChatHistory.java](/d:/0%20Postgraduate/JAVA/JAVA%20Project/Java_Project_Practices/Yupi_Projects/yu-ai-code-mother/YuCodeMother-Backend/src/main/java/com/yupi/yucodemotherbackend/model/entity/ChatHistory.java:1)。

关键字段包括：

- `message`：消息内容
- `messageType`：消息类型，区分 `user / ai`
- `appId`：消息所属应用
- `userId`：消息所属用户
- `createTime`：创建时间

消息类型枚举定义在 [ChatHistoryMessageTypeEnum.java](/d:/0%20Postgraduate/JAVA/JAVA%20Project/Java_Project_Practices/Yupi_Projects/yu-ai-code-mother/YuCodeMother-Backend/src/main/java/com/yupi/yucodemotherbackend/model/enums/ChatHistoryMessageTypeEnum.java:1)：

```java
USER("用户", "user"),
AI("AI", "ai");
```

这意味着系统在持久化时会明确区分：

- 用户发送的 prompt
- AI 返回的完整内容

#### 3. 添加聊天消息的统一入口

消息入库统一通过 [ChatHistoryService.java](/d:/0%20Postgraduate/JAVA/JAVA%20Project/Java_Project_Practices/Yupi_Projects/yu-ai-code-mother/YuCodeMother-Backend/src/main/java/com/yupi/yucodemotherbackend/service/ChatHistoryService.java:1) 的：

```java

```

对应实现位于 [ChatHistoryServiceImpl.java](/d:/0%20Postgraduate/JAVA/JAVA%20Project/Java_Project_Practices/Yupi_Projects/yu-ai-code-mother/YuCodeMother-Backend/src/main/java/com/yupi/yucodemotherbackend/service/impl/ChatHistoryServiceImpl.java:1)。

该方法完成了：

1. 参数校验
2. 消息类型合法性校验
3. 通过 Builder 快速构造 `ChatHistory`
4. 调用 `save()` 落库

这一步统一了对话历史的写入规范，避免各业务层直接拼接数据库逻辑。

### 对话记忆与业务流程集成

#### 1. 用户发消息时先落库

在 [AppServiceImpl.java](/d:/0%20Postgraduate/JAVA/JAVA%20Project/Java_Project_Practices/Yupi_Projects/yu-ai-code-mother/YuCodeMother-Backend/src/main/java/com/yupi/yucodemotherbackend/service/impl/AppServiceImpl.java:1) 的 `chatToGenCode(...)` 中，AI 调用之前先执行：

```java
chatHistoryService.addChatMessage(appId, message, ChatHistoryMessageTypeEnum.USER.getValue(), loginUser.getId());
```

这意味着用户消息的持久化时机是：

- 权限校验通过后
- 调用 AI 前
- 无论 AI 最终成功还是失败，这条用户输入都会被记录下来

这是合理的，因为用户确实已经发起了一次会话请求。

#### 2. 获取 app 专属 AI Service

随后业务层会根据 `appId` 获取 AI 服务实例：

```java
AiCodeGeneratorService aiCodeGeneratorService = aiCodeGeneratorServiceFactory.getAiCodeGeneratorService(appId);
```

这一步把“当前属于哪个应用”的上下文传给工厂层，让系统能够自动完成：

- 找到对应记忆实例
- 没有则新建
- 新建时回填历史

#### 3. AI 流式回复完成后再保存 AI 消息

因为 AI 回复是流式生成的，所以不能在一开始就直接保存完整消息。

项目采用的做法是：

```java
StringBuilder aiResponseBuilder = new StringBuilder();
return contentFlux.map(chunk -> {
    aiResponseBuilder.append(chunk);
    return chunk;
}).doOnComplete(() -> {
    String aiResponse = aiResponseBuilder.toString();
    chatHistoryService.addChatMessage(appId, aiResponse, ChatHistoryMessageTypeEnum.AI.getValue(), loginUser.getId());
});
```

这样设计的好处是：

- 前端仍然可以实时接收流式片段
- 后端同时把所有片段拼成完整回复
- 流完成后再把完整 AI 消息入库

这样数据库里保存的是一条完整 AI 回复，而不是零碎片段。

#### 4. AI 失败时也记录错误消息

如果流式生成异常，系统会在 `doOnError()` 中保存一条失败消息：

```java
String errorMessage = "AI 回复信息失败：" + error.getMessage();
chatHistoryService.addChatMessage(appId, errorMessage, ChatHistoryMessageTypeEnum.AI.getValue(), loginUser.getId());
```

这样做的价值在于：

- 后台历史里能看到这次调用失败
- 便于排查线上问题
- 对话历史链路不会因为异常完全断档

### 历史回填机制

#### 1. 回填方法的职责

历史回填的核心方法是：

```java
int loadChatHistoryToMemory(Long appId, MessageWindowChatMemory chatMemory, int maxCount);
```

实现位于 [ChatHistoryServiceImpl.java](/d:/0%20Postgraduate/JAVA/JAVA%20Project/Java_Project_Practices/Yupi_Projects/yu-ai-code-mother/YuCodeMother-Backend/src/main/java/com/yupi/yucodemotherbackend/service/impl/ChatHistoryServiceImpl.java:137)。

这个方法的目标不是简单查库，而是把数据库历史重新组装成 **LangChain4j 可理解的聊天上下文对象**。

#### 2. 查询最近历史消息

它会按 `appId` 查询最近若干条记录：

```java
QueryWrapper queryWrapper = QueryWrapper.create()
        .eq(ChatHistory::getAppId, appId)
        .orderBy(ChatHistory::getCreateTime, false)
        .limit(1, maxCount);
```

这里的实现意图是：

- 先按时间倒序查出最近消息
- 只取最近 `maxCount` 条
- 控制装载规模，避免无限恢复全部历史

#### 3. 反转为正序再加入记忆

查出来的结果是“最新在前”，但记忆重放必须按时间顺序进行，所以代码中执行了：

```java
historyList = historyList.reversed();
```

这样是为了模拟真实对话时间线：

1. 先加入更早的用户消息
2. 再加入对应的 AI 回复
3. 逐步恢复到最近状态

如果不反转，模型接收到的上下文顺序就会错，记忆恢复会失真。

#### 4. 先清空再重建记忆

回填前执行了：

```java
chatMemory.clear();
```

这一步很关键，它防止：

- 旧缓存中的消息残留
- 同一批历史被重复装载
- 已存在上下文和数据库历史混叠

所以这里采用的是“清空后按数据库重建最近窗口”的策略。

#### 5. 不同消息类型转换为不同对象

系统不会把所有消息都当普通字符串塞进记忆，而是根据消息类型分别转换：

```java
chatMemory.add(UserMessage.from(history.getMessage()));
chatMemory.add(AiMessage.from(history.getMessage()));
```

这一步很重要，因为对 LangChain4j 来说：

- 用户消息和 AI 消息在语义上不同
- 框架需要知道谁说了什么
- 否则上下文会退化成无角色文本

#### 6. 回填失败不阻塞主流程

方法整体包在 `try-catch` 中，失败时只记录日志并返回 `0`：

```java
catch (Exception e) {
    log.error("加载历史对话失败...", e);
    return 0;
}
```

这意味着即使历史恢复失败：

- 系统仍然可以继续生成代码
- 只是失去最近上下文
- 不会因为辅助能力失败而让主流程不可用

这是典型的“增强能力失败不拖垮核心链路”的后端设计思路。

### 两种实现思路与最终选择

#### 方案一：MemoryId + chatMemoryProvider

工厂类中保留了原始方案的注释代码，大意是：

- 用一个共享 AI Service
- 通过 `chatMemoryProvider(memoryId -> ...)` 为不同 `memoryId` 生成不同记忆对象

这套方案本身可行，也比较贴近 LangChain4j 的原生用法。

#### 方案二：每个 appId 对应一个独立 AI Service

本项目最终采用的是这一方案，即：

- 每个应用拿到自己的 AI Service
- 每个服务实例预先绑定自己的 `chatMemory`
- 再配合 Caffeine 做实例级缓存

#### 为什么最终更偏向方案二

因为对当前项目来说，方案二更容易承载这些业务需求：

1. 明确的应用级上下文隔离
2. 易于在创建时主动回填数据库历史
3. 易于做实例缓存和生命周期控制
4. 更符合“一个应用就是一个长期 AI 对话体”的业务抽象

换句话说，方案一更偏“框架能力实现”，方案二更偏“业务语义清晰”。

### 完整调用链

#### 后端调用链路

```text
前端发起对话生成请求
    ->
AppServiceImpl.chatToGenCode(appId, message, loginUser)
    ->
1. 校验 appId / 用户权限 / 代码生成类型
    ->
2. 保存用户消息到 chat_history
    ->
3. AiCodeGeneratorServiceFactory.getAiCodeGeneratorService(appId)
    ->
4. 如果缓存没有，则 createAiCodeGeneratorService(appId)
    ->
5. 创建 MessageWindowChatMemory(id = appId)
    ->
6. 绑定 RedisChatMemoryStore
    ->
7. 从 chat_history 装载最近 20 条历史到 chatMemory
    ->
8. 创建并返回专属 AiCodeGeneratorService
    ->
9. 调用大模型生成代码
    ->
10. 流式返回内容给前端
    ->
11. doOnComplete 中保存完整 AI 回复到 chat_history
    ->
12. 下次同 appId 请求继续复用上下文
```

#### 数据流视角

从数据流看，这一版形成了完整闭环：

```text
用户消息
    -> 数据库存档
    -> 进入当前会话记忆
    -> 送入大模型
    -> 生成 AI 回复
    -> AI 回复写入 Redis 记忆
    -> AI 回复落库保存
    -> 服务重建时再从数据库回填
```

这不是单纯的“缓存一下对话”，而是一个真正可恢复的记忆系统。

### 技术亮点

#### 1. appId 级别隔离，避免上下文串线

这是本版最核心的架构收益。

通过把 `appId` 同时用于：

- `serviceCache` 的 key
- `MessageWindowChatMemory.id(...)` 的 id
- 历史查询的 appId 条件

系统把“应用”这个业务概念贯穿到了：

- 服务实例层
- 记忆存储层
- 历史持久化层

最终达成真正的一致性隔离。

#### 2. Redis + MySQL 双层记忆设计

这一版没有把“聊天历史”和“聊天记忆”混为一谈。

它区分了两个概念：

- **聊天记忆**：服务当前推理要用的最近上下文，重视速度和窗口大小
- **聊天历史**：可查、可恢复、可审计的完整记录，重视持久化

这种分层比“只存 Redis”或“只查数据库”都更实用。

#### 3. 历史回填让记忆具备恢复能力

如果只有 Redis 记忆窗口，没有数据库回填，那么：

- 缓存一失效，上下文就断
- JVM 一重启，AI 就“失忆”

而历史回填机制让对话系统具备了“短期失忆后恢复最近状态”的能力，这对连续生成类产品非常重要。

#### 4. 缓存服务实例而不是重复造轮子

把 `AiCodeGeneratorService` 做本地缓存，说明这一版实现不只是“能跑”，还开始考虑运行时开销和服务生命周期。

这一步的本质价值是：

- 提升连续对话命中率
- 减少重复初始化成本
- 保持近期上下文稳定

### 测试与验证

#### 1. 测试目标

这部分功能最重要的不是普通单次生成是否成功，而是：

1. 同一 `memoryId` / `appId` 的连续对话是否能记住上文
2. 不同 `memoryId` / `appId` 之间是否互不干扰
3. Redis 认证是否正确

#### 2. 对话记忆测试用例

测试类在 [AiCodeGeneratorServiceTest.java](/d:/0%20Postgraduate/JAVA/JAVA%20Project/Java_Project_Practices/Yupi_Projects/yu-ai-code-mother/YuCodeMother-Backend/src/test/java/com/yupi/yucodemotherbackend/ai/AiCodeGeneratorServiceTest.java:1)。

其中 `testChatMemory()` 的设计思路很清楚：

- 先用 `memoryId = 1` 发送一次生成请求
- 再追问“你刚才做了什么”
- 然后换到 `memoryId = 2` 重复同样流程

这个测试验证了两个关键点：

1. **同一个 memoryId 内部能继承上下文**
2. **不同 memoryId 之间的对话记忆是隔离的**

#### 3. Redis 认证踩坑与修复

这部分在开发中出现过一个典型问题：

```text
redis.clients.jedis.exceptions.JedisAccessControlException: NOAUTH Authentication required.
```

根因不是 Redis 地址错误，而是：

- 项目使用的 Redis 需要认证
- LangChain4j 当前 Redis 实现对 “只传 password，不传 user” 的兼容不稳
- 导致底层实际上按“无认证连接”去访问 Redis

最终修复方式就是本版加入的：

- `spring.data.redis.username: default`
- `resolveRedisUser()` 自动补齐用户名

这一步属于实现细节，但非常关键，因为它直接决定“对话记忆能否在真实 Redis 上跑起来”。

### 与 1.0 / 1.1 的关系

#### 与 1.0 对话历史模块的关系

`1.0` 重点解决的是：

- 聊天历史怎么建表
- 怎么查询
- 怎么分页
- 怎么做权限控制

而 `1.2` 更进一步，解决的是：

- 聊天历史怎么重新参与 AI 推理
- 运行时记忆怎么建立
- 应用级对话怎么隔离
- 记忆窗口和持久化历史怎么协同

也就是说：

- `1.0` 偏“历史记录管理”
- `1.2` 偏“AI 连续对话能力”

#### 与 1.1 前端对话历史的关系

`1.1` 更多是前端视角，解决“怎么展示历史”。

而 `1.2` 是后端视角，解决“怎么让历史真正成为模型上下文的一部分”。

前端能看到历史，不代表 AI 记得历史；而 `1.2` 的价值恰恰在于把这两件事接起来了。

### 常见问题

#### 1. 为什么不能所有应用共用一个 AI Service

因为共用实例会导致：

- 会话上下文难以隔离
- 历史回填逻辑不清晰
- A 应用和 B 应用对话可能混用

#### 2. 为什么还要存数据库，Redis 不是已经有记忆了吗

因为 Redis 更像“短期工作记忆”，数据库才是“长期历史档案”。

没有数据库，就无法：

- 恢复最近历史
- 查询完整对话
- 做后台管理和分页查看

#### 3. 为什么回填时只加载最近 20 条消息

因为对话上下文不是越多越好。

限制窗口大小可以：

- 控制 token 消耗
- 保持近期上下文优先
- 避免过长历史拖慢推理

#### 4. 为什么 AI 回复要在流结束后再落库

因为流式输出过程中拿到的是片段，不是完整回答。

只有等流结束后，才能：

- 拼出完整 AI 回复
- 形成一条有意义的历史消息
- 保持数据库记录清晰

### 核心收益总结

#### 从“单次生成”升级到“连续对话生成”

这一版最重要的成果，是把 AI 零代码生成从“问一次、答一次”的请求式能力，升级成了“带上下文、可持续追问、可恢复历史”的应用式能力。

#### 形成了完整的后端记忆闭环

本版已经打通了下面这条完整链路：

- 用户发消息
- 消息落库
- 按 appId 获取独立 AI 服务
- 从 Redis / 数据库恢复最近记忆
- 调用模型生成
- 保存 AI 回复
- 下次继续沿用上下文

这说明项目在后端侧已经具备了真正的“多轮 AI 应用”基础。

#### 为后续功能奠定基础

有了这一版的对话记忆后端实现，后续很多能力才有现实基础，例如：

- 连续修改同一个应用
- 根据历史对话生成摘要
- 基于上下文做更细的代码迭代
- 更复杂的会话管理、清理和分析

### 后续可优化方向

#### 1. 记忆窗口策略优化

当前是固定 `maxMessages(20)`，后续可以进一步做成：

- 按 token 数而不是条数裁剪
- 保留系统关键消息
- 对旧对话做摘要压缩

#### 2. Redis 与数据库一致性增强

当前已经具备完整闭环，但还可以继续增强：

- 删除应用时同步清理 Redis memory key
- 历史回填前先校验 Redis 是否已有可用上下文
- 增加消息去重和修复逻辑

#### 3. 面向多租户或多用户的更细粒度隔离

目前隔离主键是 `appId`，对于当前项目是成立的。后续如果业务更复杂，可以考虑升级为：

- `userId + appId`
- `tenantId + userId + appId`

以支撑更复杂的组织结构。
